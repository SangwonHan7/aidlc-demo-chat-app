# End-to-End Test Instructions - QuickChat

## Purpose
stories.md의 7개 스토리(일반 사용자 5개 + 채널 관리자 2개)를 사용자 관점의 전체 흐름으로 확인한다. integration-test-instructions.md는 컴포넌트 간 연동(API/WS 계약이 실제로 맞물리는지)에 초점을 맞췄고, 이 문서는 화면까지 포함한 실제 사용자 여정에 초점을 맞춘다.

## 전제
`build-instructions.md`대로 전체 스택(PostgreSQL/Redis/Kafka/Vault/Backend/Frontend)이 기동되어 있어야 한다. 브라우저 2개(또는 시크릿 모드 2개 탭)로 서로 다른 사용자를 동시에 조작하는 시나리오가 많다.

## E2E 시나리오

### E2E-1: 회원가입 → 로그인 → 로그아웃 → 재로그인 (Story 1.1)
1. `/register`에서 신규 계정 생성 (표시이름/이메일/비밀번호)
2. `/login`으로 리다이렉트 확인, 로그인
3. `/`(AppShellLayout)로 리다이렉트, Sidebar에 표시이름 노출 확인
4. 로그아웃 → `/login`으로 리다이렉트 확인
5. 같은 브라우저 탭에서 **다른 계정**으로 재로그인 → 이전 사용자의 채널 목록/메시지가 전혀 보이지 않는지 확인(Frontend에서 자체 발견해 고친 `chatStore.reset()`/`presenceStore.reset()` 로그아웃 처리 검증)
6. 비밀번호를 5회 연속 틀리게 입력 → 짧은 시간 계정 잠금(423) 확인

### E2E-2: 공개 채널 생성 → 다른 사용자가 목록에서 바로 참여 (Story 1.3, 2.1)
1. 사용자 A: "새 채널" → 이름 입력, 공개(PUBLIC) 선택 → 생성
2. 사용자 B(다른 브라우저): Sidebar의 "참여 가능한 공개 채널" 섹션에 A가 만든 채널이 보이는지 확인
3. B가 "참여" 클릭 → 채널이 활성화되고 메시지를 주고받을 수 있는지 확인
4. **보안 회귀 확인(H1)**: B가 참여하지 않은 INVITE_ONLY 채널의 UUID를 (개발자 도구로) 알아내 `POST /api/channels/{id}/join`을 직접 호출 → 거부(403 FORBIDDEN_ACTION)되는지 확인

### E2E-3: 초대 전용 채널 - 초대 없이는 참여 불가, 초대받으면 가능 (Story 1.3, 2.1, 2.2)
1. 사용자 A: 초대 전용(INVITE_ONLY) 채널 생성
2. 사용자 B: 이 채널이 Sidebar의 "참여 가능한 공개 채널"에 노출되지 않는지 확인(디자인상 당연히 안 보여야 함 - discoverable API가 PUBLIC만 반환)
3. A가 멤버 관리 패널에서 B를 이메일로 검색해 초대
4. B가 채널 목록에 새로 나타난 채널을 확인하고 메시지 주고받기

### E2E-4: 1:1 DM 시작 (Story 1.2)
1. 사용자 A: DM 목록의 "새 DM 시작"에서 B를 이메일로 검색 후 시작
2. 메시지 전송 → B의 화면에 실시간 도착하는지 확인(500ms 이내 목표, `performance-test-instructions.md`)
3. **연속 메시지 확인(Patch 5 회귀)**: A가 연속으로 3개 이상 메시지를 빠르게 전송 → B의 화면에 전부(누락 없이) 표시되는지 확인 - 수정 전이었다면 두 번째 메시지부터 사라졌을 시나리오
4. DM 채널 헤더에 B의 실제 표시이름이 보이는지 확인(내부 식별자 `dm:{id1}:{id2}`가 아니라)

### E2E-5: 온라인 상태 표시 (Story 1.4)
1. A, B 모두 로그인
2. A의 화면에서 B의 PresenceIndicator가 온라인(녹색)으로 보이는지 확인
3. B가 브라우저 탭을 닫음(DISCONNECT) → A의 화면이 30초 이내(polling 주기) 오프라인(회색)으로 바뀌는지 확인
4. B가 연결을 2분 이상 유지하며 메시지를 보내지 않을 경우, TTL 갭으로 실제로는 온라인인데 오프라인으로 표시되는지 확인(`integration-test-instructions.md` Scenario 5와 동일 관찰 포인트)

### E2E-6: 메시지 이력 무한 스크롤 (Story 1.5)
1. 채널에 메시지 100개 이상 축적(스크립트로 미리 채워두거나 반복 전송)
2. 채널 진입 시 최근 메시지부터 로드되는지 확인
3. 위로 스크롤 → 이전 페이지가 추가로 로드되는지(react-window 가상화 목록에서 스크롤 위치가 튀지 않는지) 확인
4. 새로고침 후에도 동일 위치까지 이력이 다시 정상적으로 로드되는지 확인

### E2E-7: 채널 구성원 관리 - 초대/제외, 권한 경계 (Story 2.2)
1. OWNER(A)가 멤버 관리 패널을 열고 이메일로 사용자(C) 검색 후 초대
2. 일반 멤버(C)는 "멤버 관리" 버튼이 보이지 않는지 확인(ConversationHeader가 OWNER에게만 노출)
3. C가 API를 직접 호출(`POST /api/channels/{id}/members`)해 다른 사용자를 초대 시도 → 403 확인
4. A가 C를 제외 → C의 화면에서 해당 채널이 사라지는지, C가 이후 그 채널의 `/topic/channel/{id}`를 구독해도 메시지를 받지 못하는지 확인(H2 수정 검증과 연결)
5. A(OWNER)가 스스로 채널을 나감 → 채널이 ARCHIVED로 전환되고 남은 멤버 화면에 "보관됨"으로 표시되는지 확인

## 알려진 제약 (투명성 목적)
위 7개 시나리오는 이번 세션에서 실행된 적이 없다(브라우저 자동화 도구나 실제 기동 환경이 없었음). E2E-2의 4번, E2E-4의 3번, E2E-7의 4번은 이번 Build and Test 단계에서 새로 발견/수정한 보안 결함(H1, Patch 5, H2)에 대한 실제 재현/회귀 확인이라 우선순위가 가장 높다.
