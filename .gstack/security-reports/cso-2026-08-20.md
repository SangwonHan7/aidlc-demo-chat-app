> **사후 조치 업데이트 (2026-08-20, 같은 날 후속 조치)**: 이 보고서 제출 직후, H1과 H2는 명백한 접근 제어 로직 결함이라 판단해 코드를 즉시 수정했습니다(설계 트레이드오프가 아니라 이미 승인된 스펙과 실제 구현이 어긋난 버그였음). 함께 발견된 M1(WebSocket CORS 전면 허용)도 REST와 동일한 origin 제한으로 좁혔습니다.

> - M1: `WebSocketConfig.registerStompEndpoints()`가 `quickchat.cors.allowed-origin`(REST와 동일한 값)을 사용하도록 수정.

## 3. 상세 발견 항목

### HIGH

```
[HIGH] [9/10] 채널 참여(join) API에 가시성(visibility) 검증 누락 → INVITE_ONLY/DM 채널 무단 참여
(backend/src/main/java/com/quickchat/backend/service/ChannelService.java:73-78,
 backend/src/main/java/com/quickchat/backend/web/ChannelController.java:60-63)

Type    : Broken Access Control / Missing Authorization (로직 결함)
OWASP   : A01 Broken Access Control
ISMS-P  : 2.6.1 네트워크 접근통제, 2.6.2 정보시스템 접근통제
CWE     : CWE-862 Missing Authorization (관련: CWE-284 Improper Access Control)
Exploit : joinChannel()의 Javadoc은 "PUBLIC 채널 자율 참여"라고 명시하지만, 실제 코드는
          getChannelOrThrow(channelId)로 채널을 조회한 뒤 그 반환값(channel)의
          visibility를 한 번도 검사하지 않고 바로 ChannelMember를 저장합니다.
          따라서 인증된 임의 사용자가 POST /api/channels/{channelId}/join 을
          INVITE_ONLY 그룹 채널이나 1:1 DIRECT(DM) 채널의 UUID로 호출하면,
          한 번도 초대받지 않았어도 정상적으로 멤버가 됩니다. 이후에는
          GET /api/channels/{channelId}/messages(멤버십만 확인)로 전체 대화
          이력을 읽고, WebSocket으로 메시지를 보낼 수도 있습니다(ChatFacadeService도
          멤버십만 확인). 채널 UUID는 무작위 UUIDv4라 무차별 추측은 비현실적이지만,
          다른 멤버가 링크를 붙여넣거나, 브라우저 히스토리/네트워크 탭, 캡처화면 등으로
          유출되는 경로는 충분히 현실적입니다. inviteMember()는 OWNER만 가능하도록
          올바르게 막혀 있어, 이 join 경로가 그 통제를 완전히 무력화하는 "우회 문"이 됩니다.
Fix     : joinChannel()에 `if (channel.getVisibility() != ChannelVisibility.PUBLIC) throw
          new ForbiddenActionException();` 를 requireNotAlreadyMember() 이전에 추가하고,
          DIRECT 채널 타입도 함께 차단(ChannelType.GROUP만 허용)하십시오. 회귀 테스트로
          "INVITE_ONLY/DIRECT 채널에 대한 join 시도는 항상 거부된다"는 속성(PBT)을
          추가하는 것을 권고합니다(이 프로젝트는 이미 jqwik 기반 PBT 관행을 사용 중).
기한    : 배포 전 필수 (standard/strict 차단)
재점검  : 수정 후 48시간 내
```

[HIGH] [8/10] STOMP 구독(SUBSCRIBE) 목적지에 멤버십 인가 검증이 전혀 없음 → 임의 채널 실시간 도청
(backend/src/main/java/com/quickchat/backend/websocket/WebSocketConfig.java:28-32,
 backend/src/main/java/com/quickchat/backend/websocket/StompAuthChannelInterceptor.java:44-68)

Type    : Broken Access Control / Missing Authorization (설계 결함)
OWASP   : A01 Broken Access Control
ISMS-P  : 2.6.1 네트워크 접근통제, 2.6.2 정보시스템 접근통제
CWE     : CWE-862 Missing Authorization / CWE-284 Improper Access Control
Exploit : WebSocketConfig가 `/topic`을 Spring 내장 SimpleBroker로 그대로 노출하고,
          유일한 ChannelInterceptor인 StompAuthChannelInterceptor는 CONNECT(인증)와
          DISCONNECT(presence 정리)만 가로챕니다 — SUBSCRIBE 커맨드는 검사하지 않습니다.
          `@EnableWebSocketSecurity`, simpDestMatchers/simpSubscribeDestMatchers 등
          목적지별 인가 설정도 저장소 전체에서 발견되지 않았습니다(그렙으로 확인).
          따라서 유효한 JWT로 WebSocket에 CONNECT만 하면(=시스템에 계정만 있으면),
          어떤 채널의 멤버가 아니어도 `/topic/channel/{임의의 channelId}`를 그대로
          SUBSCRIBE 할 수 있고, 그 순간부터 그 채널에 실시간으로 오가는 모든 메시지를
          수신합니다. REST 이력 조회(과거分)와 메시지 전송(쓰기)은 각각 별도로 멤버십을
          검사하므로 이 경로로는 "과거 이력 열람"이나 "메시지 전송"은 되지 않지만,
          ChannelMember 레코드가 전혀 생성되지 않아 흔적 없이 미래 시점의 대화를
          엿들을 수 있다는 점에서 은밀성이 높습니다. H1(join 우회)과 결합하면 한 계정으로

Fix     : `AbstractSecurityWebSocketMessageBrokerConfigurer`(spring-security-messaging)를
          도입하거나, 기존 ChannelInterceptor에 SUBSCRIBE 분기를 추가해 목적지의
          channelId를 파싱한 뒤 ChannelService.isMember(channelId, principalUserId)를
          호출하고 실패 시 예외를 던져 구독을 거부하도록 수정하십시오. 프론트엔드
          stompClient.subscribeToChannel()은 이미 인증된 흐름에서만 호출되므로
          정상 사용자 경험에는 영향이 없습니다.
기한    : 배포 전 필수 (standard/strict 차단)
재점검  : 수정 후 48시간 내

### MEDIUM

```
[MEDIUM] [7/10] WebSocket STOMP CORS 전면 허용(`*`) — REST CORS 정책과 불일치
(backend/src/main/java/com/quickchat/backend/websocket/WebSocketConfig.java:25)

Type    : Security Misconfiguration (Origin 검증 불일치)
OWASP   : A05 Security Misconfiguration
ISMS-P  : 2.6.1 네트워크 접근통제
CWE     : CWE-346 Origin Validation Error
Exploit : SecurityConfig.corsConfigurationSource()는 REST API의 Origin을
          quickchat.cors.allowed-origin 한 곳으로 명시적으로 제한하며 주석으로 그
          이유(Bearer 토큰 인증이라 쿠키 credential은 필요 없지만 Origin은 제한)를
          설명합니다. 그런데 WebSocketConfig.registerStompEndpoints()는
          `setAllowedOriginPatterns("*")`로 모든 Origin의 WebSocket CONNECT 시도를
          허용합니다. 현재는 인증이 STOMP CONNECT 프레임의 Authorization 헤더(Bearer
          토큰)로 이뤄지고 그 토큰은 localStorage에만 있어 제3자 페이지가 SOP상 직접
          읽을 수 없으므로, "즉시 계정 탈취"로 이어지는 실증 경로는 이번 점검에서
          확인하지 못했습니다(과장하지 않기 위해 명시). 다만 이는 (1) 문서화된 REST
          CORS 정책과 일관되지 않은 신뢰 경계이고, (2) 향후 토큰 저장 방식이 쿠키 기반으로
          바뀌거나 M5(localStorage 저장)와 별도의 XSS가 결합될 경우 즉시 크로스오리진
          세션 하이재킹으로 악화되는 잠재적 증폭 지점입니다.
Fix     : registerStompEndpoints()에도 REST와 동일한
          `${quickchat.cors.allowed-origin}` 값을 setAllowedOrigins()로 지정하십시오.
          와일드카드가 필요한 이유가 있다면(예: 여러 배포 환경) 명시적 화이트리스트
          배열로 좁히십시오.
기한    : 배포 후 2주 이내
재점검  : 수정 후 1주 내 재점검
```

## 5. STRIDE Threat Model (Phase 10)

### 5.1 Auth 컴포넌트 (register/login/refresh/JWT)
- **Spoofing**: BCrypt 검증 + HMAC 서명 JWT로 자격증명·토큰 위조는 어려움. 잔여 위험은 JWT_SECRET이 실제 배포 시 Vault/k3s Secret에서 올바르게 주입되는지에 의존(L6로 검증 범위 밖).
- **Tampering**: JWT는 서명으로 보호, refresh token은 서버측 Redis 조회 방식(불투명 랜덤 UUID)이라 클라이언트가 값을 바꿔도 의미가 없음. 낮은 위험.
- **Repudiation**: 로그인 성공/실패에 대한 별도 감사로그(구조화 로그)가 코드상 보이지 않음 — 사후 조사 시 애플리케이션 로그 외 근거가 부족할 수 있음(정보 없음, 별도 심각도 부여하지 않고 권고로만 기록).
- **Information Disclosure**: L2(회원가입 이메일 열거). 로그인 자체는 사용자 존재 열거를 막음(양호).
- **Denial of Service**: M9(이메일 단위 잠금의 표적형 DoS 악용 가능성).
- **Elevation of Privilege**: 별도 관리자/역할 상승 지점 없음. 낮은 위험.

### 5.2 Channel/Membership 컴포넌트
- **Spoofing**: 해당 없음 (사용자 신원은 Auth 컴포넌트에 위임).
- **Tampering**: 멤버십 캐시(MembershipCacheService)는 5분 TTL의 positive-only 캐시로, 캐시 미스 시 항상 DB로 진실을 확인하도록 설계되어 캐시 오염으로 인한 권한 상승 경로는 발견하지 못함(양호). 다만 `removeMember` 직후에도 짧은 시간 동안 캐시가 남아있어 즉시 반영되지 않는 5분 이하의 지연 창이 이론상 존재 — invalidate()가 명시적으로 호출되므로(코드 확인) 실질적 위험은 낮음.
- **Repudiation**: channel_members에 joined_at, OWNER/MEMBER role 기록(양호).
- **Information Disclosure**: M2(사용자 조회 API).
- **Denial of Service**: L7(채널 생성/참여 rate limit 없음).
- **Elevation of Privilege**: **H1** — 비멤버가 join으로 정식 MEMBER 권한을 얻는 것 자체가 권한 상승입니다.

### 5.3 Messaging 컴포넌트 (WebSocket + Kafka + Redis Pub/Sub)
- **Spoofing**: senderId는 항상 서버측 Principal에서만 취득(SendMessageStompRequest는 content만 전달) — 클라이언트가 발신자를 위조할 수 없음(양호).
- **Tampering**: Kafka JsonDeserializer가 TRUSTED_PACKAGES를 com.quickchat.backend.kafka로 제한해 역직렬화 가젯 공격 표면을 최소화(양호, INFO I3).
- **Repudiation**: messages 테이블에 sender_id/sent_at 기록(양호).
- **Information Disclosure**: **H2** — 구독 경로 인가 부재로 인한 도청.
- **Denial of Service**: 전송측 rate limit 존재(양호, L5의 경계 버스트만 잔여). 브로드캐스트 실패는 로그만 남기고 저장은 이미 완료된 상태를 유지하도록 설계되어(MessagingService.broadcastMessage try/catch) 부분 장애가 데이터 손실로 이어지지 않음(양호).
- **Elevation of Privilege**: H1과 결합 시 도청을 넘어 쓰기 권한까지 획득 가능.

### 5.4 Presence 컴포넌트
- **Spoofing**: sessionId/userId는 STOMP CONNECT 인증 결과에서만 파생(양호).
- **Tampering**: Redis Set 기반 세션 카운팅으로 멱등적 markOnline(양호, 설계 문서와 일치 확인).
- **Repudiation**: 해당 없음(보안 감사 대상 아님).
- **Information Disclosure**: GET /api/presence?userIds=는 인증만 요구하고 관계 검증이 없어 M2와 동일한 패턴이지만 노출되는 정보(온라인/오프라인 불리언)가 극히 제한적이라 별도 항목 없이 M2에 흡수.
- **Denial of Service**: 하트비트 기반 TTL 갱신 로직이 아직 없다는 점이 코드 주석에 이미 "알려진 제약"으로 명시되어 있음 — 장시간 연결 시 presence 정확도 저하 가능성이 있으나 보안 문제는 아님(기능 결함으로 분류, 별도 심각도 부여 안 함).
- **Elevation of Privilege**: 해당 없음.

## 15. 종합 권고 및 한계 (Disclosure)

1. **BLOCKED 판정의 실질적 의미**: 이번 감사는 standard 게이트 기준(HIGH ≤2)을 1건 초과해 기계적으로 BLOCKED입니다. 그중 H3(Spring Boot EOL)는 즉시 착수 가능한 업그레이드 작업이고, H1·H2는 코드 로직 결함으로 각각 한두 줄 수준의 수정으로 해결 가능합니다. 세 건 모두 수정 후 재점검(48시간 내)을 통과하면 즉시 PASS로 전환될 수 있는 성격입니다 — "심각한 구조적 재설계가 필요한" 상태는 아닙니다.
2. **감사자의 한계**: 이 점검은 정적 코드 판독 + WebSearch만으로 수행되었고 실제 실행/침투 테스트는 하지 않았습니다. H1·H2는 코드 판독으로는 매우 명확하지만, 배포 전 반드시 실제 환경(dev/staging)에서 curl/Postman/WS 클라이언트로 재현 테스트를 1회 수행해 확인하는 것을 권고합니다.
3. **k3s 매니페스트 부재(L6)**: "production" 배포 대상의 실제 인프라 코드가 아직 저장소에 없어, 이번 감사는 애플리케이션 코드와 두 Dockerfile, 로컬/폴백용 docker-compose까지만 다뤘습니다. k3s 매니페스트가 작성되면 Phase 5(인프라 표면)를 그 시점에 반드시 재실행하십시오.
