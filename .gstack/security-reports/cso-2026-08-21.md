## 2. H1 / H2 / M1 수정 검증 (독립 재확인)

### H1 — 채널 join API 가시성 검증 (RESOLVED)
파일: `backend/src/main/java/com/quickchat/backend/service/ChannelService.java:78-87` (joinChannel)

현재 코드:
```java
@Transactional
public void joinChannel(UUID channelId, UUID userId) {
    Channel channel = getChannelOrThrow(channelId);
    if (channel.getVisibility() != ChannelVisibility.PUBLIC) {
        throw new ForbiddenActionException();
    }
    requireNotAlreadyMember(channelId, userId);
    memberRepository.save(new ChannelMember(channelId, userId, ChannelRole.MEMBER));
    membershipCache.cacheMember(channelId, userId);
}
```
검증 결과: **실제로 수정됨, 유효**. `ChannelVisibility` enum은 `PUBLIC`, `INVITE_ONLY` 두 값만 가지며(`ChannelVisibility.java` 확인), `getOrCreateDirectChannel()`이 DIRECT 채널을 항상 `ChannelVisibility.INVITE_ONLY`로 생성함을 `ChannelService.java:64-65`에서 확인했습니다. 따라서 "visibility != PUBLIC" 검사 하나로 08-20 보고서가 요구한 두 가지(INVITE_ONLY 그룹 채널 차단, DIRECT 채널 차단)가 모두 커버됩니다 — 별도의 `ChannelType` 검사가 없어도 기능적으로 충분합니다. 회귀 테스트 `ChannelServiceTest.java`도 저장소에 존재함을 확인했습니다(내용까지는 이번 점검에서 정독하지 않음).

### H2 — STOMP SUBSCRIBE 인가 (RESOLVED)
파일: `backend/src/main/java/com/quickchat/backend/websocket/StompAuthChannelInterceptor.java:79-101`

현재 코드에는 `StompCommand.SUBSCRIBE` 분기가 추가되어 `requireMembershipForSubscription()`을 호출합니다. 이 메서드는 (1) 목적지가 `/topic/channel/`로 시작하지 않으면 통과(다른 브로커 목적지가 없으므로 무해), (2) Principal이 없으면 예외, (3) 목적지에서 channelId를 파싱해 `channelService.requireMember(channelId, userId)`를 호출 — 멤버가 아니면 `NotAMemberException`이 던져져 구독이 거부됩니다. **실제로 수정됨, 유효**. CONNECT 시점에 설정된 Principal(`accessor.setUser(...)`)이 이후 SUBSCRIBE 프레임에서도 그대로 조회되는 Spring 세션 동작에 의존하는데, 이는 08-20 보고서가 이미 확인한 정상 동작과 일치합니다.

### M1 — WebSocket CORS 전면 허용 (RESOLVED)
파일: `backend/src/main/java/com/quickchat/backend/websocket/WebSocketConfig.java:34-36`

`registerStompEndpoints()`가 이제 `setAllowedOriginPatterns("*")`가 아니라 생성자로 주입된 `${quickchat.cors.allowed-origin}` 값(`allowedOrigin` 필드)을 사용합니다. `SecurityConfig.corsConfigurationSource()`가 REST에 사용하는 것과 동일한 프로퍼티 키입니다. **실제로 수정됨, 유효** — REST와 WebSocket의 신뢰 경계가 이제 일치합니다.

**결론**: 세 건 모두 claim대로 수정되었고, 수정 내용도 기술적으로 타당합니다. "수정했다고 주장했지만 실제로는 안 됐거나 불완전한" 경우는 발견되지 않았습니다.

## 5. 이번 세션에서 발견된 그 외 코드 변경 사항 — 신규 보안 결함 여부 확인

담당자가 언급한 "WebSocket 메시지 필드명 버그 수정"(`RedisBroadcastListener`, `MessageResponse.from(ChatMessageEvent)`)을 확인했습니다.

- `RedisBroadcastListener.java`: Redis Pub/Sub에서 받은 `ChatMessageEvent`를 `MessageResponse.from(event)`로 변환해 `/topic/channel/{channelId}`로 재전송하도록 바뀌었습니다. 이전에는 내부 이벤트(필드명 `messageId`)를 그대로 내보내 프론트엔드가 기대하는 `id` 필드가 없어지는 **기능 버그**였습니다.
- `MessageResponse.from(ChatMessageEvent event)` 신규 팩토리 메서드를 `MessageResponse.java`에 확인했습니다. `ChatMessageEvent`(record: `messageId, channelId, senderId, content, sentAt`)의 필드를 `MessageResponse`(record: `id, channelId, senderId, content, sentAt`)로 1:1 매핑만 수행합니다.

**결론: 정보 노출(information disclosure) 관점에서 새로운 문제 없음.** `ChatMessageEvent`에는 REST `MessageResponse.from(Message)` 경로가 이미 노출하는 필드(id/channelId/senderId/content/sentAt) 외의 내부 전용 필드(예: 트레이스 ID, 재시도 횟수, 원본 예외 등)가 없음을 `ChatMessageEvent.java` 정독으로 확인했습니다. 즉 이 버그 수정은 이미 존재하던 인가 경계(H2 수정으로 SUBSCRIBE 시점에 멤버십 검증됨)를 넘어서는 어떤 새 데이터도 추가로 흘려보내지 않습니다.

이 외에 저장소를 다시 둘러보며 08-20 이후 추가된 것으로 보이는 파일(`ChannelServiceTest.java`, `StompAuthChannelInterceptorTest.java`, `RedisBroadcastListenerTest.java` 등 회귀 테스트)도 확인했으나, 이들은 테스트 전용 코드로 Phase 12 기본 제외 규칙에 따라 발견 항목 대상이 아닙니다. 그 외 신규 REST/WS 엔드포인트, 신규 설정 파일, 신규 인프라 정의는 발견되지 않았습니다.

**신규(New) 발견 항목: 0건.**

## 11. 종합 권고 및 한계

1. **PASS 판정의 실질적 의미**: standard 게이트 기준으로는 PASS이지만, H3(Spring Boot EOL)이라는 라이프사이클 리스크가 여전히 남아있고 MEDIUM 8건·LOW 8건이 미해결 상태입니다. "당장 배포 차단은 아니지만 안전하다"는 뜻은 아닙니다.
2. **strict 게이트였다면 여전히 BLOCKED**: 08-20 보고서가 언급했듯, PII·채팅 콘텐츠를 다루는 서비스 특성상 strict 게이트(HIGH 0건 허용)를 기준으로 하면 H3 하나만으로도 이번에도 BLOCKED입니다. 담당자·정보보안팀은 이 서비스에 standard가 적절한 기준인지 재확인하시기 바랍니다(08-20 보고서에서도 동일하게 권고).
3. **커밋 미확정 상태 지속**: H1/H2/M1 수정은 여전히 커밋되지 않은 작업 트리 변경입니다. 실제 배포 파이프라인에 들어갈 정식 커밋을 만들고, 그 커밋 해시로 최종 재점검을 한 번 더 수행할 것을 강하게 권고합니다.
4. **재검증 범위의 한계**: 이번 점검은 "baseline과의 차이"에 집중한 위험 기반 재검증이며, 145개 전체 파일을 처음부터 다시 훑은 전면 재감사가 아닙니다. 특히 인증 토큰 발급/검증 경로(JwtTokenProvider 등)는 이번에 다시 읽지 않았습니다 — 08-20 이후 그 파일들이 변경되지 않았다는 보장은 git diff가 아니라 "언급되지 않았다"는 정황적 근거에만 의존합니다. 다음 정기 점검(예: 배포 직전)에서는 전체 재정독을 권고합니다.
