# Vision Document: QuickChat Team Messaging App

> AI-DLC 데모용 요구사항 문서입니다. (1회차 멘토링 라이브 데모 — 실제 팀 프로젝트 주제와는 무관한 별도 예시입니다.)

## Executive Summary

QuickChat은 조직 내 팀원들이 1:1 대화와 그룹 채널을 통해 실시간으로 메시지를 주고받을 수 있는 사내 메신저 웹 애플리케이션이다. 이메일과 흩어진 협업 툴로 인해 발생하는 소통 지연과 정보 파편화 문제를 해결하기 위해, 실시간 전송과 채널 기반 대화 이력을 하나의 서비스로 제공한다. 기대 효과는 팀 내 평균 응답 시간 단축과 협업 도구 통합에 따른 커뮤니케이션 효율 향상이다.

## Business Context

### Problem Statement

많은 소규모 조직/팀이 이메일, 메신저, 사내 게시판 등 여러 도구에 커뮤니케이션이 흩어져 있어 대화 이력을 추적하기 어렵고, 실시간성이 낮아 의사결정이 지연된다. 특히 프로젝트 단위로 빠르게 소통해야 하는 팀에게는 가볍고 빠른 자체 메신저가 필요하다.

### Business Drivers

- 재택/하이브리드 근무 확산으로 비동기+실시간 텍스트 커뮤니케이션 수요 증가
- 외부 SaaS 메신저 도입 시 발생하는 데이터 보안/외부 반출 우려 → 자체 구축 필요
- 사내 시스템(사원 정보, 알림 등)과의 연동을 전제로 한 확장 가능성

### Target Users and Stakeholders

| User Type | Description | Primary Need |
|-----------|-------------|---------------|
| 일반 사용자 (팀원) | 실시간으로 동료와 대화하는 조직 구성원 | 빠르고 안정적인 메시지 송수신, 대화 이력 확인 |
| 채널 관리자 | 팀/프로젝트 채널을 생성하고 구성원을 관리하는 사용자 | 채널 생성·구성원 초대·권한 관리 |
| 시스템 운영자 | 서비스 운영/모니터링 담당자 | 장애 조기 감지, 트래픽 급증 대응 |

### Business Constraints

- 데모/실습 목적의 소규모 프로젝트로, AWS 등 퍼블릭 클라우드 계정이 아직 준비되지 않아 자체 NAS 인프라 위에서 구축·운영 (클라우드 비용 대신 NAS의 CPU/메모리/스토리지 용량이 제약 조건)
- 개발 인력은 소수(팀 단위) 인원으로, 짧은 기간 내 핵심 기능부터 검증
- 개인정보(로그인 계정, 대화 내용)를 다루므로 최소한의 보안 기준은 반드시 충족

### Success Metrics

| Metric | Current State | Target State | Measurement Method |
|--------|---------------|---------------|---------------------|
| 메시지 전달 지연 (p50) | N/A | 500ms 미만 | 서버 로그 기반 송신-수신 타임스탬프 비교 |
| 동시 접속 처리 | N/A | 500 동시 접속 세션 안정 처리 | 부하 테스트 (WebSocket 연결 유지) |

## Full Scope Vision

### Product Vision Statement

QuickChat은 조직이 별도의 외부 SaaS 없이도 안전하고 빠른 실시간 커뮤니케이션 기반을 스스로 운영할 수 있게 하는 사내 메신저 플랫폼으로 성장한다.

### Feature Areas

#### Feature Area 1: 실시간 메시징

- **Description**: 1:1 및 그룹 채널 기반의 실시간 텍스트 메시지 송수신
- **Key Capabilities**:
  - 1:1 다이렉트 메시지
  - 그룹 채널 생성 및 참여
  - 실시간 전송 (WebSocket)
  - 온라인/오프라인 상태 표시
- **User Value**: 이메일 대비 즉각적인 소통, 대화 이력의 채널 단위 정리

#### Feature Area 2: 알림 및 검색

- **Description**: 새 메시지 알림과 과거 대화 검색
- **Key Capabilities**:
  - 읽지 않은 메시지 뱃지/알림
  - 키워드 기반 메시지 검색
  - 멘션(@) 알림
- **User Value**: 중요한 메시지를 놓치지 않고, 과거 논의 내용을 빠르게 재확인

#### Feature Area 3: 협업 확장 기능 (장기)

- **Description**: 파일 공유, 화면/음성 통화, 외부 시스템 연동
- **Key Capabilities**:
  - 파일/이미지 첨부
  - 음성/영상 통화
  - 사내 시스템(사원 정보, 캘린더) 연동 Webhook
- **User Value**: 메신저를 넘어선 협업 허브로 확장

### Integration Points

- **사내 인증 시스템** (장기) - SSO 연동
- **모니터링 스택** (Prometheus/Grafana 등) - 서비스 상태 관측
- **알림 채널** (이메일/푸시, 장기) - 오프라인 사용자 알림

### User Journeys (Full Vision)

#### Journey 1: 새 팀 채널 개설과 협업

1. 채널 관리자가 새 프로젝트 채널을 생성한다.
2. 팀원들을 채널에 초대한다.
3. 팀원들이 실시간으로 메시지를 주고받으며 파일도 공유한다.
4. 과거 논의가 필요할 때 키워드로 검색해 다시 확인한다.

**Outcome**: 프로젝트 관련 대화가 한 채널에 정리되어 추적 가능해진다.

### Scalability and Growth

- 사용자/채널 수 증가에 따라 WebSocket 연결을 여러 서버(파드)로 분산하고, 메시지 브로커(Kafka)와 캐시(Redis)로 상태를 공유해 수평 확장
- 장기적으로 모바일 앱, 외부 시스템 연동, 다국어 지원으로 확장 가능

### Long-Term Roadmap

| Phase | Focus | Timeframe |
|-------|-------|-----------|
| MVP | 1:1/그룹 실시간 메시징, 온라인 상태, 기본 알림 | 데모 1일차 |
| Phase 2 | 검색, 파일 첨부, 읽음 확인 | 추후 |
| Phase 3 | 모바일 앱, 외부 시스템 연동, 음성/영상 | 추후 |

## MVP Scope

### MVP Objective

핵심 실시간 메시징(1:1 + 그룹 채널)이 안정적으로 동작하는 것을 증명하고, 이를 통해 AI-DLC 워크플로우가 요구사항부터 아키텍처, 코드 생성까지 이어지는 과정을 시연한다.

### MVP Success Criteria

- [ ] 로그인한 두 사용자가 1:1로 실시간 메시지를 주고받을 수 있다
- [ ] 그룹 채널을 생성하고 여러 사용자가 참여해 메시지를 주고받을 수 있다
- [ ] 메시지 전송 시 500ms 이내에 수신자 화면에 표시된다
- [ ] 접속 중인 사용자의 온라인 상태가 표시된다

### Features In Scope (MVP)

| Feature | Description | Priority | Rationale for Inclusion |
|---------|--------------|----------|---------------------------|
| 회원가입/로그인 | 이메일+비밀번호 기반 인증, JWT 발급 | Must Have | 메신저 이용의 최소 전제 조건 |
| 1:1 다이렉트 메시지 | 두 사용자 간 실시간 메시지 송수신 | Must Have | 가장 기본적인 핵심 가치 |
| 그룹 채널 | 채널 생성, 참여, 채널 내 메시지 송수신 | Must Have | 팀 단위 협업의 핵심 시나리오 |
| 실시간 전송 | WebSocket(STOMP) 기반 실시간 푸시 | Must Have | "실시간" 가치 제안의 핵심 |
| 온라인 상태 표시 | 사용자 접속 여부 표시 | Should Have | 소통 가능 여부를 즉시 파악 |
| 메시지 이력 조회 | 채널/DM의 과거 메시지 페이지 조회 | Must Have | 대화 맥락 파악에 필수 |

### Features Explicitly Out of Scope (MVP)

| Feature | Reason for Deferral | Target Phase |
|---------|----------------------|----------------|
| 파일/이미지 첨부 | 저장소·용량 정책 설계가 추가로 필요 | Phase 2 |
| 메시지 검색 | 별도 검색 인덱싱 설계 필요 | Phase 2 |
| 읽음 확인 | 부가 기능으로 MVP 검증에는 불필요 | Phase 2 |
| 음성/영상 통화 | 구현 범위가 크고 별도 인프라 필요 | Phase 3 |
| 모바일 앱 | 데모 범위는 웹으로 한정 | Phase 3 |
| 외부 시스템 연동(SSO 등) | 초기 검증 이후 우선순위 재검토 | Phase 3 |

### MVP User Journeys

#### Journey 1: 1:1 실시간 대화

1. 사용자 A가 로그인한다.
2. 사용자 B를 검색해 다이렉트 메시지를 연다.
3. 메시지를 입력해 전송한다.
4. 사용자 B의 화면에 실시간으로 메시지가 표시된다.

**Outcome**: 두 사용자가 지연 없이 대화한다.
**Limitation vs Full Vision**: 파일 첨부, 읽음 확인 없음.

#### Journey 2: 그룹 채널 협업

1. 사용자 A가 "공지" 채널을 생성한다.
2. 사용자 B, C를 채널에 초대한다.
3. 세 사용자가 채널에서 메시지를 주고받는다.

**Outcome**: 여러 사용자가 하나의 채널에서 동시에 협업한다.
**Limitation vs Full Vision**: 채널 검색·아카이브 기능 없음.

### MVP Constraints and Assumptions

- **Assumption**: 사용자 규모는 소규모(수백 명 이내)로 시작한다 - **Risk if wrong**: 대규모 트래픽 시 재설계 필요
- **Accepted Limitation**: 인증은 자체 이메일/비밀번호 방식만 지원 (소셜 로그인 미지원)

### MVP Definition of Done

- [ ] MVP 기능 전체 구현 및 기본 테스트 통과
- [ ] Kubernetes 환경에 배포되어 접근 가능
- [ ] 기본 보안 점검(인증, 입력값 검증) 완료

## Risks and Dependencies

### Key Risks

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| WebSocket 연결이 다중 파드 환경에서 세션 불일치를 일으킬 수 있음 | Medium | High | 자체 호스팅 Redis 기반 Pub/Sub로 파드 간 메시지 브로드캐스트 |
| 메시지 유실 (서버 재시작/장애 시) | Low | High | Kafka를 메시지 버퍼/이벤트 로그로 사용, 컨슈머 재처리 |
| 짧은 데모 기간 내 범위 초과 | Medium | Medium | MVP 범위를 엄격히 제한, Out of Scope 항목 명확화 |

### External Dependencies

- **Kubernetes 클러스터** - 자체 NAS 서버에 구축 (k3s 등 경량 배포판) - 가용
- **Kafka, Redis, Vault** - 자체 NAS 인프라에 컨테이너로 직접 구축 (관리형 클라우드 서비스 아님) - 가용
- **AWS 등 퍼블릭 클라우드 계정** - 아직 지원되지 않음, 준비되면 인프라 마이그레이션 검토 - 미가용
